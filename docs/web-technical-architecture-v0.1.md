# 同频 Web 产品技术方案 v0.1

## 1. 文档目的

本文定义“同频”网页产品的第一版技术架构，覆盖客户端、服务端、数据、匹配流程、安全合规、部署和验证方式。

本文以 [关系信号与匹配指标 v0.1](./matching-metrics-v0.1.md) 为产品和数据约束。若两者冲突，以隐私、同意和安全要求更严格的一方为准。

## 2. 范围与总体决策

### 2.1 范围

- 最终交付形态是响应式网页产品，同时支持桌面和移动浏览器。
- 用户端、运营审核端和 API 服务均采用 Web 技术。
- 第一阶段服务 30–50 名首批用户，重点验证问题设计、推荐解释和 7/14 天结果闭环。
- 中国大陆作为首要部署和数据驻留区域。

### 2.2 非目标

- 不开发 iOS、Android 或桌面原生客户端。
- 不使用 Electron。浏览器已经是最终运行环境，额外封装不会带来产品价值。
- 第一阶段不拆分微服务，不引入 Kubernetes、Kafka、独立推荐平台或独立向量数据库。
- 不导入未经明确授权的第三方聊天或通讯录数据。
- 不在第一阶段依赖复杂深度学习排序模型。

PWA 可以作为后续增强能力，但核心流程不能依赖 PWA 才能完成。

## 3. 架构原则

1. **隐私默认拒绝**：没有有效 `consent_scope` 的数据，不进入匹配链路。
2. **原始内容与排序隔离**：原始文本只用于生成经过审核的 Evidence 和 Claim，不能直接作为最终排序输入。
3. **服务端掌握业务真相**：浏览器不直接访问数据库，也不接收内部排序分数。
4. **模块化单体优先**：先保持一个可部署的后端，以清晰模块隔离变化，压力出现后再拆分。
5. **事件可追溯**：推荐、曝光、互动和结果均记录 `model_version`、`policy_version` 和来源。
6. **解释面向关系线索**：API 返回共同点、差异点和未知信息，不返回匹配百分比、星级或人格标签。
7. **安全可以否决推荐**：安全事件和硬约束优先于普通排序结果。
8. **先测量，再学习**：先运行规则和文本基线，积累结果数据后再训练排序模型。

## 4. 总体架构

```text
用户浏览器 / 管理端浏览器
          |
       HTTPS / WSS
          |
   CDN + WAF + 反向代理
          |
   +------+-------------------------------+
   |                                      |
Next.js Web / Admin                  FastAPI API
                                           |
                 +-------------------------+-------------------------+
                 |                         |                         |
          PostgreSQL + pgvector        Redis + Queue             对象存储
                 |                         |                    OSS / COS
                 |                         |
                 +------------------ Celery Worker
                                           |
                                     离线任务 / 模型训练
```

用户端与管理端只通过 API 访问业务数据。Next.js 可以负责服务端渲染、静态资源和受限的服务端数据获取，但不能复制后端领域规则。

## 5. 技术栈

| 层级 | 选择 | 主要职责 |
|---|---|---|
| 用户 Web | Next.js + TypeScript | 页面、登录后的交互、公开说明页和服务端渲染 |
| 管理 Web | Next.js + TypeScript | 安全审核、数据权利请求、策略和模型版本查看 |
| UI 基础 | Tailwind CSS + Radix/shadcn | 组件、主题、可访问性和响应式布局 |
| 前端状态 | TanStack Query + 少量本地状态 | 服务端状态缓存、请求重试和乐观更新 |
| 表单校验 | React Hook Form + Zod | 问卷、资料和取舍题校验 |
| API | FastAPI + Pydantic + SQLAlchemy 2 + Alembic | 业务 API、权限校验、匹配编排和数据迁移 |
| 主数据库 | PostgreSQL | 用户、同意、Evidence、Claim、匹配、事件和审计 |
| 向量检索 | pgvector | 文本表示和候选召回；第一阶段不拆独立向量库 |
| 缓存与队列 | Redis + Celery | 短时缓存、限流、异步任务和定时任务 |
| 实时通信 | WebSocket + Redis Pub/Sub | 对话、在线状态和匹配状态更新 |
| 文件存储 | 腾讯云 COS / 阿里云 OSS | 用户明确上传的材料、加密存储和短期签名地址 |
| 可观测性 | OpenTelemetry + Sentry + 结构化日志 | 请求追踪、前后端异常和关键任务告警 |
| 测试 | pytest + Vitest + Playwright | 单元、集成、契约和端到端测试 |

Python 是后端首选，因为 Claim 处理、指标计算、实验和模型训练主要集中在同一技术生态。若团队完全以 TypeScript 为主，可以替换为 NestJS/Fastify，但模型训练仍应保持独立 Python 服务，不能因此省略数据契约。

## 6. 建议仓库结构

```text
apps/
  web/                 # 用户端 Next.js
  admin/               # 管理端 Next.js，可独立部署
services/
  backend/
    app/api/           # FastAPI 路由和依赖
    app/modules/       # 领域模块
    app/workers/       # Celery 任务
    migrations/        # Alembic 迁移
packages/
  contracts/           # OpenAPI 生成客户端与共享 Schema
infra/
  compose/             # 本地和测试环境
  deploy/              # 部署配置
tests/
  e2e/                 # 端到端与合规回归测试
```

管理端与用户端共享设计基础包，但不共享认证 Cookie，也不把管理功能打包进用户端资源。

## 7. 后端领域模块

| 模块 | 职责 |
|---|---|
| Identity | 账号、手机号验证、会话、设备与登录安全 |
| Consent | 同意范围、版本、撤回、数据保留和授权检查 |
| Evidence | 原始材料的受控引用、脱敏、证据元数据和来源追踪 |
| Claims | Claim 生成、确认、修正、过期、稳定性和敏感等级 |
| Matching | 硬约束、双人特征、候选召回、排序、探索和解释生成 |
| Interaction | 邀请、对话、通知、举报、拉黑和边界反馈 |
| Outcomes | 7/14/30 天结果调查、结果变量和实验指标 |
| Safety | 风控事件、审核结果、封禁和安全否决规则 |
| Admin | RBAC、策略版本、人工审核、审计和数据权利请求 |

模块在同一进程内通过明确接口调用，通过数据库事务保证一致性。禁止跨模块任意访问内部表。

## 8. 数据架构

### 8.1 数据存储边界

- PostgreSQL 是业务事实的唯一来源。
- Redis 只保存可重建的缓存、锁和任务队列，不作为最终事实来源。
- 原始材料保存在对象存储中，数据库只保存受控引用、来源、同意范围和生命周期状态。
- Claim、特征快照和解释因素可在 PostgreSQL 中使用 JSONB，但关键筛选和关联字段必须结构化。
- 第一阶段事件先以追加写方式保存在 PostgreSQL，并通过事务 Outbox 异步处理；数据规模增长后再同步到 ClickHouse。

### 8.2 核心数据域

```text
身份与授权：users, sessions, consents
证据与信号：raw_documents, evidence, claims, feature_snapshots
匹配与实验：pair_features, impressions, actions, matches
模型与策略：model_versions, policy_versions
互动与结果：conversations, outcomes, safety_events
系统可靠性：outbox_events, idempotency_keys, audit_logs
```

所有结构变更必须通过 Alembic 迁移，禁止直接修改生产数据库结构。

### 8.3 数据生命周期

用户撤回同意后，系统必须停止将相关数据用于匹配，并阻止后续召回。删除请求需要处理对象存储原件、结构化记录、派生 Claim、缓存和搜索索引，同时保留不含原始内容的审计墓碑。

原始内容和敏感信息的保留期限必须配置化，不得由业务代码随意延长。

## 9. API 与实时通信

### 9.1 API 约定

- 业务接口统一使用 `/api/v1`。
- FastAPI OpenAPI 文档是接口契约来源，TypeScript 客户端由契约生成，避免手写重复类型。
- 浏览器与 API 使用同源反向代理，认证采用 `HttpOnly`、`Secure`、`SameSite` Cookie。
- 浏览器不接收内部排序分数、成功概率或未经过解释编译的模型特征。
- 修改类接口支持幂等键，防止重复邀请、重复提交问卷和重复记录结果。
- API 返回稳定错误码和追踪 ID，不返回数据库异常、内部 SQL 或规则实现细节。
- Next.js 不直接连接 PostgreSQL，也不复制 Claim、匹配和安全规则。

### 9.2 实时通信

- WebSocket 用于对话、已读状态和匹配过程更新。
- SSE 可用于单向通知；部署条件不适合时退化为轮询。
- 服务端以 Redis Pub/Sub 在多实例间转发事件。
- 消息写入 PostgreSQL 后再确认发送，断线重连按游标补拉，避免只存在于内存中的消息。

核心通知同时提供站内消息。Web Push 可以作为增强渠道，但由于浏览器和 iOS 限制，不能成为唯一通知方式。

## 10. 匹配与解释流程

每次推荐按以下顺序执行：

1. 检查双方同意范围和关系目标。
2. 执行地域、年龄范围、婚恋状态、不可协商项等硬约束。
3. 过滤过期、置信度过低或来源不合法的 Claim。
4. 生成双人关系信号 `pair_features`。
5. 运行当前排序策略，并保留探索性位置。
6. 应用安全否决规则。
7. 生成共同点、差异点和未知信息。
8. 记录曝光、排序位置、`model_version`、`policy_version` 和 `consent_scope`。

第一阶段的排序候选依次为：

- 硬规则与基础关系信号；
- 文本表示相似度；
- Claim 关系信号加产品内行为；
- 数据量足够后再评估逻辑回归、LightGBM 或其他排序模型。

`ranking_score`、`success_probability` 和原始 `explanation_factors` 只存在于后端。返回浏览器的推荐 DTO 只能是面向用户的线索、差异、未知项和建议。

## 11. 安全与合规

- 在服务层统一执行 `consent_scope` 校验，默认拒绝。
- 年龄、地域、职业等 L1 数据最小化采集；L2 推断必须可见、可修改、可删除。
- 不推断健康、宗教、性取向、政治倾向等 L3 敏感属性。
- 不采集、存储或训练未经授权的第三方聊天和通讯录数据。
- 传输使用 TLS，数据库、备份和对象存储使用静态加密，密钥交由 KMS 管理。
- 管理端使用独立认证和 RBAC，敏感操作写入不可篡改审计日志。
- 文件下载使用短期签名地址，登录用户也不得直接获得长期公共 URL。
- 对登录、问卷、推荐、邀请、对话、举报和导出接口实施速率限制。
- 配置 CSP、CSRF 防护、安全响应头、WAF 和依赖漏洞扫描。
- 按《个人信息保护法》、推荐算法、数据安全和生成合成内容相关适用要求进行法律评审。

## 12. 可观测性与指标

所有请求生成 `trace_id`，关键异步任务生成 `job_id`。日志不记录原始聊天、完整自述、访问令牌或敏感 Claim 内容。

第一阶段至少采集：

- 数据质量：Claim 覆盖率、证据覆盖率、过期比例、用户纠正率。
- 模型质量：PR-AUC、NDCG@K、校准误差、双向匹配率。
- 界面表达：固定人格标签违例、匹配百分比违例、差异和未知信息覆盖率。
- 产品结果：首轮回复率、7 天对话存活率、14 天满意度、30 天成长同向性和边界尊重。
- 安全护栏：举报率、拉黑率、骚扰事件、删除请求处理时间。

推荐解释、指标和事件字段必须能够关联到 `model_version` 与 `policy_version`。

## 13. 测试策略

- 后端单元测试覆盖 Claim 生命周期、硬约束、安全否决、同意校验和解释生成。
- 集成测试使用真实 PostgreSQL 和 Redis，验证事务、Outbox、幂等和删除流程。
- OpenAPI 契约测试确保 API、生成客户端和前端类型一致。
- Playwright 覆盖从问卷、推荐、邀请、对话到结果反馈的完整网页流程。
- 隐私测试验证撤回同意后不再召回、删除请求覆盖原始与派生数据、审计不保留正文。
- UI 文案回归测试禁止出现匹配百分比、星级、等级、固定人格标签和确定性措辞。
- 模型离线评估使用时间切分，不以随机切分结果作为上线依据。

发布要求是相关测试和检查全部通过。任何跳过测试的发布必须留下明确记录和补测计划。

## 14. 部署与环境

环境划分为本地开发、预发布和生产。三套环境使用独立数据库、Redis、对象存储前缀和密钥。

推荐部署方式：

- Docker 容器运行 Next.js、FastAPI 和 Celery Worker。
- 使用国内云区域的托管 PostgreSQL、Redis 和对象存储。
- CDN、WAF 和反向代理统一 HTTPS、WSS、限流和同源访问。
- CI 执行格式检查、静态检查、单元测试、契约测试、前端构建和迁移检查。
- CD、数据库迁移和回滚均需要审批与审计记录。
- PostgreSQL 开启自动备份和时点恢复，并定期验证恢复流程。

第一阶段不使用 Kubernetes。单机容器编排或托管容器服务足以支撑首批用户。出现明确容量或隔离需求后，再拆分 Worker、实时服务和模型服务。

## 15. 分阶段实施

| 阶段 | 交付内容 | 退出条件 |
|---|---|---|
| P0 基础框架 | Next.js、FastAPI、PostgreSQL、Redis、认证、同意和审计骨架 | 登录、同意记录、撤回和删除流程测试通过 |
| P1 冷启动闭环 | 问卷、Evidence/Claim、规则匹配、推荐解释、邀请、7/14 天结果 | 首批用户可完成完整闭环，所有推荐事件可追溯 |
| P2 Web 实时体验 | 对话、通知、举报、拉黑和运营审核台 | 断线重连、审核、安全否决和通知降级测试通过 |
| P3 数据驱动优化 | 特征快照、实验框架、模型校准、ClickHouse 评估 | 离线指标和线上结果稳定，满足公平与安全门槛 |

## 16. v0.1 验收标准

1. 用户可以通过响应式网页完成注册、授权、问卷、推荐、邀请、对话和结果反馈。
2. 网页不显示匹配百分比、星级、等级或固定人格标签。
3. 浏览器请求和前端资源中不存在内部排序分数与敏感模型特征。
4. 每个 Claim 都有来源、证据、置信度、时效性和修正入口。
5. 未经授权数据不会进入 Evidence、Claim、匹配、对话分析或训练集。
6. 推荐事件完整记录曝光位置、`model_version`、`policy_version` 和 `consent_scope`。
7. 安全事件和硬约束可以否决普通推荐。
8. 用户撤回和删除请求覆盖原始数据、派生数据、缓存和索引。
9. 单元、集成、契约、端到端、隐私和 UI 文案测试全部通过。

## 17. 后续需要确认的问题

- 首发域名、云厂商和 ICP 备案主体。
- 对话使用自建 WebSocket 还是经过数据保护评审的云 IM。
- 首批结果调查的触达方式，以及 Web Push、短信和邮件的优先级。
- 文本 Embedding 的部署方式、数据出境边界和模型许可。
- 管理端是否与用户端使用不同域名和独立认证系统。
