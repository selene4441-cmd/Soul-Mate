# 同频匹配后交流产品方案 v0.1

## 1. 文档目的

本文定义“同频”在完成数据处理、关系信号生成和候选匹配之后，如何让双方从关系线索进入真实交流，并形成可验证、可撤回、可安全结束的产品闭环。

本文承接以下文档：

- [关系信号与匹配指标 v0.1](./matching-metrics-v0.1.md)
- [同频 Web 产品技术方案 v0.1](./web-technical-architecture-v0.1.md)

若本文与上述文档存在冲突，以隐私、同意和安全要求更严格的一方为准。

本文是 v0.1 产品设计基线，不代表当前代码已经全部实现。现有仓库中的邀请、Match、Conversation、Message 和 WebSocket 是原型能力，后续实现必须按本文补齐双方接受、会话生命周期、安全退出和指标事件。

## 2. 产品判断

匹配后的核心问题不是“如何提供一个聊天框”，而是：

> 如何让两个仅通过结构化线索认识的人，在低压力、边界清晰且双方同意的前提下，通过一次具体交流继续确认关系可能性。

普通即时通信产品默认用户已经建立联系，因此从空白输入框开始。同频的用户只拥有共同点、差异和未知项，直接进入空白聊天会产生三个问题：

1. 用户不知道第一句话说什么，容易只发“你好”后无话可聊。
2. 匹配解释与真实交流断开，用户无法围绕需要确认的差异继续了解。
3. 邀请、拒绝、结束和拉黑缺少正式状态，容易形成骚扰或沟通压力。

因此，同频交流产品的核心对象不是消息，而是：

> 一段由具体议题开始、双方明确同意、随时可以安全结束的关系进程。

## 3. 产品定位与原则

### 3.1 产品定位

匹配后交流产品用于承接推荐结果，帮助用户完成：

`关系线索 → 选择议题 → 发起连接 → 双向接受 → 引导交流 → 继续或结束 → 结果反馈`

### 3.2 核心原则

1. **先同意，后交流**：连接请求被接受前不创建会话，也不允许发送消息。
2. **先议题，后聊天**：第一版会话从一个可追溯的共同点、差异或未知项开始，不从空白输入框开始。
3. **双向有效同意**：邀请、接受和每次发送消息都检查双方有效的 `conversation:v1` 授权。
4. **解释与交流连续**：会话中保留推荐时的关系线索快照，但不展示内部排序分数。
5. **系统不冒充用户**：系统议题必须明确标记为交流提示，不能生成看起来像对方发出的消息。
6. **边界优先于活跃**：不追求消息数量、在线时长、连续互动天数或回复速度。
7. **拒绝和结束不需要解释**：用户可以拒绝、停止交流或拉黑，不承担说服对方的义务。
8. **安全动作立即生效**：拉黑、举报和结束交流优先于普通产品体验和实时连接状态。
9. **交流内容默认不进入匹配模型**：消息正文只有在取得单独、明确且可撤回的授权后才可用于训练或推断。
10. **所有关键行为可追溯**：连接请求、接受、拒绝、会话开启、结束、拉黑和举报均记录事件与版本。

## 4. 目标用户与核心任务

### 4.1 目标用户

- 已完成问卷和 Claim 确认，能够查看关系线索的用户。
- 对某个候选人有继续了解意愿，但不愿立即进入无主题聊天的用户。
- 收到连接请求，需要判断是否愿意投入一次具体交流的用户。
- 已经交流一段时间，需要继续、降温或安全结束的用户。

### 4.2 核心任务

| 阶段 | 用户任务 | 产品需要回答的问题 |
|---|---|---|
| 理解 | 我为什么会对这个人有兴趣 | 共同点、差异和未知项是什么 |
| 选择 | 我想确认哪一个具体问题 | 有没有适合开始交流的议题 |
| 发起 | 如何表达愿意进一步了解 | 能否附上自己确认过的开场说明 |
| 回应 | 我是否愿意和对方交流 | 对方是谁、想聊什么、我有何选择 |
| 交流 | 如何自然地继续了解 | 当前上下文、可讨论议题和反馈入口在哪里 |
| 结束 | 如何不再继续且保持安全 | 怎样结束、静音、拉黑和举报 |
| 反馈 | 这次交流带来了什么结果 | 7/14/30 天关系结果如何反馈 |

## 5. 核心对象与状态机

### 5.1 ConnectionRequest

`ConnectionRequest` 表示一次有明确接收方的了解邀请，不等同于 Match，也不预先创建 Conversation。

状态定义：

```text
pending
  -> accepted
  -> declined
  -> cancelled
  -> expired
```

规则：

- 只有推荐关系中双方都存在有效 `matching:v1` 时可创建。
- 创建时双方都必须具备有效 `conversation:v1`；任一方后续撤回授权时，所有待处理请求失效。
- 请求包含推荐解释快照、所选议题、可选个人说明、策略版本和过期时间。
- 默认 7 天未回应后进入 `expired`，具体时限配置化。
- 被拒绝后进入冷却期，默认 30 天内不允许同一发起人再次请求，避免持续施压。
- 同一对用户最多存在一个待处理请求，重复提交必须通过幂等键返回同一结果。
- 真实用户不能因 `is_seed`、演示模式或后台开关自动进入 `accepted`。

### 5.2 Match

`Match` 表示双方已经建立可继续了解的关系连接，只在连接请求被接受后创建。

建议增加以下生命周期字段：

```text
accepted_at
closed_at
closed_by
close_reason
```

### 5.3 Conversation

`Conversation` 表示双方已开启的对话，一个接受后的 Match 最多对应一个进行中的 Conversation。

状态定义：

```text
active
closed
blocked
```

规则：

- `active`：双方授权有效，且没有任何一方结束或拉黑。
- `closed`：任一方主动结束交流后对双方停止发送，历史保留范围按隐私策略处理。
- `blocked`：任一方拉黑另一方后立即停止发送、通知和再次连接。
- 会话成员分别维护自己的提醒状态、退出状态和最后阅读位置。

### 5.4 ConversationCue

`ConversationCue` 是从推荐关系线索生成的低压力交流议题。

允许类型：

- `common`：从共同点继续了解。
- `difference`：围绕需要确认的差异交流。
- `unknown`：把未知项变成具体问题。
- `boundary`：确认联系频率、独处时间、隐私和拒绝方式。
- `custom`：用户自己修改或编写的议题。

议题必须包含来源、版本和面向用户的暂定表达，禁止将模型推断写成绝对事实。

## 6. 核心用户流程

### 6.1 发起连接

1. 用户从关系线索进入候选人详情页。
2. 页面展示共同点、差异、未知项和继续了解建议。
3. 系统提供 2–3 个候选议题，用户可以修改或自行填写。
4. 用户可附上一句由本人确认的开场说明。
5. 发送前再次检查双方授权、安全状态、冷却期和重复请求。
6. 请求进入 `pending`，不会创建 Conversation。

### 6.2 回应连接

1. 接收方进入“等你回应”，查看请求、关系线索、议题和发起人说明。
2. 接收方可选择“愿意聊聊”或“暂不联系”。
3. 接受前再次检查双方授权和安全状态。
4. 接受后，在同一事务中创建 Match、Conversation、成员记录和首个系统议题。
5. 拒绝不要求填写理由，理由只作为接收方私有信息，不直接反馈给发起人。
6. 请求过期、撤回或授权失效时，不展示为普通未读消息。

### 6.3 交流

1. 会话顶部展示双方选择的关系线索快照和当前议题。
2. 系统议题以独立卡片出现，不伪装成对方消息。
3. 双方可以回应议题、继续普通文字交流或忽略议题。
4. 消息先写入服务端再显示为成功，断线后按游标补拉。
5. 发送失败保留本地草稿和重试入口，不允许出现只在本地存在的“已发送”假象。
6. 未读状态只用于帮助用户找到消息，不以精确已读、在线状态或输入状态制造回复压力。

### 6.4 继续或结束

1. 用户可以选择“继续了解”“暂时静音”或“结束交流”。
2. 结束交流后双方均不能继续发送消息，但可以查看允许保留的历史。
3. 用户可以选择拉黑，拉黑立即阻止双方继续联系，且不向对方泄露拉黑操作细节。
4. 用户可以举报具体用户或消息，举报时保留可审计引用，但日志不保存完整消息正文。

## 7. 功能需求

### 7.1 P0：双向连接与会话生命周期

| ID | 需求 | 验收要点 |
|---|---|---|
| CONN-01 | 创建有议题的连接请求 | 请求包含议题、个人说明和推荐解释快照 |
| CONN-02 | 接收方接受或拒绝 | 只有接收方可改变 `pending` 请求 |
| CONN-03 | 接受后创建会话 | 接受前不存在可用 Conversation |
| CONN-04 | 冲突和过期处理 | 重复请求返回同一结果，过期后不可接受 |
| CONN-05 | 双方授权校验 | 任一方撤回 `conversation:v1` 后停止发送 |
| CONN-06 | 审计与指标事件 | 请求、接受、拒绝、撤回和过期均有事件 |
| MSG-01 | 消息可靠发送 | 服务端提交成功后才显示成功，支持幂等重试 |
| MSG-02 | 实时更新与降级 | WebSocket 更新，轮询仍可完成核心流程 |
| MSG-03 | 会话状态控制 | 结束或拉黑后禁止继续发送 |
| SAFE-01 | 结束交流 | 任一方可单方面结束，立即生效 |
| SAFE-02 | 拉黑 | 立即停止消息、通知和再次连接 |
| SAFE-03 | 举报 | 可关联用户、会话和具体消息 |

### 7.2 P1：差异化引导交流

| ID | 需求 | 验收要点 |
|---|---|---|
| CUE-01 | 基于关系线索生成议题 | 议题可追溯到 Claim 或双人信号 |
| CUE-02 | 用户选择与修改 | 用户确认后才进入连接请求 |
| CUE-03 | 会话上下文 | 会话顶部保留开启时的解释快照 |
| CUE-04 | 系统议题标识 | 明确展示“交流提示”，不冒充任何用户 |
| CUE-05 | 议题反馈 | 用户可标记“有帮助”“不相关”或自行忽略 |
| FEED-01 | 结果反馈入口 | 可在合适时间进入 7/14/30 天反馈 |
| FEED-02 | 指标事件 | 记录首条消息、首轮回复、持续交流和结束原因类别 |

### 7.3 v0.1 非目标

- 群聊、多人语音、视频、公开社区和动态信息流。
- 图片、文件、语音消息等复杂消息类型。
- 在线状态、输入中状态和强提醒式精确已读回执。
- 连续互动天数、消息排行榜或其他活跃压力设计。
- 由 AI 代替用户发送消息、模拟对方人格或自动维持关系。
- 将未单独授权的消息正文直接送入匹配模型。
- 在 PostgreSQL 和 Redis 之外引入新的消息中间件。

## 8. 页面与交互

### 8.1 候选人详情页

保留现有共同点、差异、未知项和继续了解建议，并新增：

- 推荐议题选择。
- 可编辑的个人开场说明。
- 发送前隐私与双方同意说明。
- 已存在请求时的状态展示，避免重复发起。

### 8.2 “等你回应”页面

展示：

- 发起人基础信息。
- 关系线索摘要和所选议题。
- 发起人本人确认过的说明。
- “愿意聊聊”“暂不联系”和举报入口。
- 请求过期时间，不使用倒计时制造紧迫感。

### 8.3 会话页

结构建议：

```text
会话上下文：共同点 / 差异 / 未知项
当前议题：可回应的具体问题
消息区：普通消息和系统议题卡
输入区：文字、草稿、发送失败重试
安全入口：静音、结束交流、拉黑、举报
```

交互规则：

- 明确区分自己和对方的消息。
- 不展示“对方正在输入”。
- 不展示精确“已读时间”；内部可维护阅读位置用于未读计数。
- 结束或拉黑后输入区关闭，并给出清晰解释。
- 举报流程不得要求用户反复接触冒犯内容。

### 8.4 通知

- 第一版仅提供站内通知和低频摘要。
- 新连接请求可以通知一次，不重复催促。
- 普通消息可以批量摘要，不追求即时触达。
- 被拒绝、结束或拉黑后不再发送相关催促通知。
- WebSocket 只负责状态同步，不替代可靠的服务端通知记录。

## 9. 数据模型

### 9.1 connection_requests

```text
id
requester_id
recipient_id
recommendation_id
session_id
source_feature_ids
topic_text
personal_message
status
policy_version
expires_at
responded_at
declined_reason_private
created_at
updated_at
```

约束：

- 同一对用户同一时间最多一个有效 `pending` 请求。
- `requester_id` 与 `recipient_id` 不能相同。
- 接受和拒绝操作必须使用事务与条件更新，防止并发响应。

### 9.2 matches

在现有表上增加：

```text
accepted_at
closed_at
closed_by
close_reason
```

### 9.3 conversations

在现有表上增加：

```text
status
context_snapshot
opened_at
closed_at
last_message_at
```

`context_snapshot` 只保存用户可见的关系线索和版本引用，不保存内部排序分数。

### 9.4 conversation_members

```text
conversation_id
user_id
last_read_at
notification_state
exited_at
blocked_at
created_at
```

该表用于每个用户独立的未读位置、静音和退出状态，不向另一方暴露精确阅读时间。

### 9.5 conversation_cues

```text
id
conversation_id
cue_type
text
source_feature_ids
source_versions
created_by
status
created_at
```

### 9.6 messages

在现有表上增加：

```text
kind
reply_to_id
deleted_at
moderation_status
```

现有 `client_message_id` 继续用于幂等发送。消息正文不进入常规日志和通用分析事件。

### 9.7 blocks

```text
id
blocker_id
blocked_id
reason_private
created_at
revoked_at
```

拉黑的默认效果不依赖 Conversation 是否仍然存在，避免通过创建新请求绕过。

## 10. API 契约

目标接口：

```text
POST   /api/v1/connection-requests
GET    /api/v1/connection-requests?direction=incoming|outgoing
POST   /api/v1/connection-requests/{id}/accept
POST   /api/v1/connection-requests/{id}/decline
DELETE /api/v1/connection-requests/{id}

GET    /api/v1/conversations
GET    /api/v1/conversations/{id}
GET    /api/v1/conversations/{id}/messages
POST   /api/v1/conversations/{id}/messages
POST   /api/v1/conversations/{id}/close

POST   /api/v1/blocks
DELETE /api/v1/blocks/{user_id}
POST   /api/v1/safety/reports
```

接口规则：

- 所有修改接口要求 CSRF 防护和当前用户会话。
- 连接请求、接受、拒绝、消息和举报支持 `Idempotency-Key`。
- 接受、拒绝和拉黑使用条件更新，重复请求不能产生重复 Match 或 Conversation。
- 消息列表使用游标分页，不一次返回全部历史。
- WebSocket 事件必须能够在断线后由 REST 游标补齐。
- 错误响应继续使用稳定错误码，不暴露数据库和规则实现。
- 现有 `/invitations` 和 `/matches/{id}/messages` 可在迁移期保留兼容层，但新客户端使用目标接口。

## 11. 事件与指标

### 11.1 核心事件

```text
connection_request_created
connection_request_accepted
connection_request_declined
connection_request_expired
connection_request_cancelled
conversation_opened
conversation_cue_created
message_sent
message_delivered
conversation_closed
user_blocked
safety_report_created
```

所有事件至少包含：

```text
event_id
event_time
actor_id
recipient_id
request_id
match_id
conversation_id
message_id
policy_version
context
```

### 11.2 核心指标

- 连接请求接受率。
- 接受后 7 天内开启交流的比例。
- 首轮回复率。
- 7 天对话存活率。
- 14 天双向满意度。
- 30 天成长同向满意度。
- 30 天时间、空间和边界被尊重比例。
- 现实见面率。
- 结束交流率和撤回授权率。

### 11.3 反指标与安全护栏

- 拒绝后的重复请求率必须为 0。
- 结束、拉黑或撤回授权后的消息发送量必须为 0。
- 举报率、拉黑率和骚扰事件率。
- 单向投入严重失衡的会话比例。
- 用户因回复压力而关闭通知或结束交流的比例。
- 未授权消息正文进入模型训练的事件数必须为 0。
- 删除、撤回授权和举报请求的处理时长。

产品优化目标应是双向接受后的高质量交流，不是消息数量、在线时长或日活时长。

## 12. 安全与隐私

- `conversation:v1` 必须由双方有效授权，并在接受请求和每次发送消息时重新校验。
- 任一方撤回授权后，后续发送立即停止；历史内容的保留和删除按已声明策略执行。
- 拉黑是单向且立即生效的动作，不依赖对方同意。
- 举报可以引用具体消息 ID，但审计日志和通用监控不得保存完整正文。
- 拒绝理由和拉黑理由默认仅接收方或操作者可见，不向被拒绝者展示。
- 消息正文默认不得用于广告、画像、匹配训练或未声明的第三方用途。
- 删除账号时处理用户资料、消息、索引、缓存和备份保留策略，并保留不含正文的审计墓碑。
- 对话速率限制应同时覆盖单会话、账号和 IP 维度，并对重复邀请、消息轰炸和批量举报进行防护。
- 生产环境需要静态加密、密钥管理、消息保留策略、管理端 RBAC 和安全事件响应流程。
- 涉及未成年人、敏感个人信息、私密通信和自动化推荐时，必须完成单独法律与安全评审。

## 13. 实施顺序

### 阶段一：双向连接闭环

1. 将真实用户的邀请改为 `ConnectionRequest` 状态机。
2. 接受后创建 Match、Conversation 和首批成员记录。
3. 双方授权检查覆盖邀请、接受和消息发送。
4. 种子自动连接进入测试夹具，不进入真实用户路径。
5. 补齐拒绝、过期、撤回、结束和审计事件。

### 阶段二：议题式开场

1. 从推荐解释生成 2–3 个候选议题。
2. 用户选择、编辑并确认议题。
3. 会话保存解释快照和系统议题卡。
4. 记录议题使用与后续交流结果的关系。

### 阶段三：安全与连续性

1. 拉黑、举报引用、会话结束和通知摘要。
2. 游标补拉、Redis Pub/Sub 多实例转发和可靠重试。
3. 7/14/30 天结果反馈与推荐指标闭环。
4. 管理端安全审核、滥用检测和数据权利处理。

## 14. v0.1 验收标准

1. 两个真实测试账号可以完成“请求 → 接受 → 交流 → 结束”的完整流程。
2. 接受请求前不存在可用 Conversation，也不能发送消息。
3. 连接请求的个人说明和所选议题能够被接收方正确看到。
4. 接受后自动创建 Match、Conversation、成员记录和系统议题。
5. 任一用户撤回 `conversation:v1` 后，双方都不能继续发送新消息。
6. 结束交流、拉黑或安全否决后消息发送立即停止。
7. 举报可以关联用户、会话和具体消息，但普通日志不记录消息正文。
8. 拒绝后的重复邀请被冷却策略和服务端校验阻止。
9. WebSocket 断开后，用户仍能通过游标补拉完整消息。
10. 推荐解释快照在会话中可查看，但不包含内部排序分数或匹配百分比。
11. 核心事件能够计算接受率、首轮回复率和 7 天对话存活率。
12. 所有新增产品、契约、权限和安全测试通过。

## 15. 待产品评审

- 连接请求默认有效期是否采用 7 天。
- 拒绝后的默认冷却期是否采用 30 天。
- 结束交流后历史记录是双方保留、仅操作者保留，还是按更短期限删除。
- 是否允许用户主动解除拉黑，或只通过客服和安全流程处理。
- 系统议题在首轮对话中的展示时长与忽略方式。
- 站内摘要通知的默认频率和关闭策略。
- 消息正文未来若用于模型训练，需单独设计的授权、脱敏和撤回机制。
