# 关系信号与匹配指标 v0.1

## 1. 文档目的

定义从原始数据到关系信号和匹配决策的第一版数据语言，回答四个问题：

1. 哪些数据可以采集，哪些数据默认禁止采集。
2. 原始内容如何转换成有证据、可修正的关系信号。
3. 单人关系信号如何组成双人相处线索。
4. 如何用真实关系结果衡量推荐是否有效，同时避免在界面把用户标签化。

本文是产品与数据设计初稿，不构成法律意见。涉及敏感个人信息、第三方数据和自动化推荐时，必须经过法律与安全评审。

## 2. 核心原则

1. 匹配的基本单位是用户对 `(A, B)`，不是单个用户的静态画像。
2. 所有推断信号必须包含证据、置信度、时效性和来源。
3. 用户必须能够查看、纠正和删除影响匹配的推断结果。
4. 原始文本不直接进入最终排序模型，只用于生成经过审核的结构化 Claim。
5. 匹配模型预测的是关系结果概率，不是对一个人的价值判断。
6. 用户界面不得把模型推断表达成固定人格标签，例如“你是回避型”“他是理性型”。
7. 内部可以维护概率和排序字段，但这些字段不能直接映射成用户可见的匹配百分比、星级或等级。
8. 未展示的候选人不能默认视为负样本；必须记录推荐策略和曝光位置。
9. 安全、同意和隐私是不可协商的硬约束。

## 3. 数据分级与来源

| 等级 | 数据 | 默认策略 |
|---|---|---|
| L0 | 用户主动公开、非敏感的内容 | 可用于明确授权的匹配目的 |
| L1 | 年龄、地域、职业等基础个人信息 | 最小必要采集，明确用途 |
| L2 | 价值观、情感需求、冲突方式等推断 | 允许用户确认、修改和删除 |
| L3 | 健康、宗教、性取向、政治倾向等敏感推断 | 默认不推断，不得用于匹配 |
| L3X | 未授权的第三方聊天、通讯录、私密关系数据 | 禁止采集和使用 |

允许的数据来源：

- 用户主动填写的问卷和资料。
- 用户主动上传、确认的自述文本。
- 产品内部的曝光、选择、互动和反馈事件。
- 用户明确授权并经过脱敏的文本资料。
- 匹配后的结果调查。

默认禁止的数据来源：

- 抓取第三方平台的非公开数据。
- 未经明确授权导入完整聊天记录。
- 根据行为暗中推断敏感属性。
- 将用户数据用于未声明的广告或第三方用途。

## 4. Claim：最小可追溯关系信号

原始内容必须先转换为 Claim：

```json
{
  "claim_id": "claim_001",
  "user_id": "user_001",
  "dimension": "life_pace",
  "value": "偏好低强度周末",
  "claim_type": "state",
  "evidence_ids": ["evidence_001"],
  "confidence": 0.72,
  "stability": "low",
  "observed_at": "2026-09-12T10:00:00+08:00",
  "expires_at": "2026-10-12T10:00:00+08:00",
  "sensitivity": "L1",
  "user_editable": true,
  "user_confirmed": false
}
```

`claim_type` 取值：

- `fact`：用户确认的客观事实。
- `preference`：偏好和取舍。
- `state`：当前状态，可能短期变化。
- `behavior`：产品内可观察行为。
- `inference`：由模型推断，必须允许纠正。

禁止把 `inference` 直接写成 `fact`。

## 5. 用户关系信号 v0.1

以下内容是可随时间变化的关系信号，不是用户画像标签。内部可以按信号域组织数据，但界面必须使用“目前更接近”“可能更看重”等暂定表达。

| ID | 信号域 | 示例 | 主要来源 | 匹配用途 |
|---|---|---|---|---|
| C1 | 关系目标 | 长期关系、婚姻、约会 | 用户填写 | 硬约束和阶段匹配 |
| C2 | 基础约束 | 地域、年龄范围、婚恋状态 | 用户填写 | 可用性过滤 |
| V1 | 核心价值 | 家庭、事业、诚信、自由 | 问卷、确认后的文本 | 长期兼容性 |
| V2 | 不可协商项 | 生育、异地、消费底线 | 取舍题、用户确认 | 硬冲突检测 |
| G1 | 成长同向性 | 成长方向、变化节奏、支持自主、共同修正关系 | 自述、情境选择、互动结果 | 长期方向与节奏兼容 |
| L1 | 生活节奏 | 作息、社交强度、工作强度 | 文本、行为、问卷 | 现实可行性 |
| M1 | 沟通方式 | 主动、直接、回复频率、话题深度 | 问卷、产品互动 | 互动体验预测 |
| R1 | 冲突修复 | 回避、协商、道歉、修复意愿 | 情境选择、互动结果 | 关系稳定性预测 |
| E1 | 情感需求 | 陪伴、空间、确认、稳定感 | 取舍题、自述 | 需求匹配 |
| T1 | 时间边界 | 回复预期、可联系时段、守约与安排变更 | 取舍题、产品互动 | 避免时间压迫和安排冲突 |
| T2 | 空间与自主 | 独处、隐私、社交、家庭和关系节奏边界 | 取舍题、用户确认、互动结果 | 避免控制和窒息感 |
| B1 | 行为一致性 | 自述偏好与真实选择是否一致 | 选择与曝光日志 | 校正自述偏差 |
| S1 | 安全与信任 | 边界、举报、骚扰、可信度 | 平台事件、审核结果 | 安全硬约束 |

关键定义：

- 成长同向性不是职业、收入或人生进度相同，而是双方对变化方向、变化节奏和彼此自主成长的支持程度相近。
- 成长同向性不意味着要求对方改变。以爱为名强迫对方成长，属于边界风险。
- 时间尊重包括回复预期、守约、安排变更、专注时间和独处时间的相互保护。
- 空间与自主尊重包括社交、隐私、家庭、身体和心理边界，不把控制、查岗或持续侵入解释为关心。

每个关系信号至少需要以下元数据：

```text
feature_id
user_id
value
confidence
coverage
recency
stability
evidence_count
user_confirmed
sensitivity
computed_at
```

## 6. 双人关系信号

双人关系信号必须同时描述 A 与 B，不能简单把两个用户画像相加。

| ID | 双人关系信号 | 计算方向 | 主要作用 |
|---|---|---|---|
| P1 | 硬约束通过 | 必须同时满足 | 决定是否允许推荐 |
| P2 | 价值观一致度 | 相似度与关键项一致 | 长期兼容性 |
| P3 | 不可协商项冲突 | 冲突数量与严重度 | 一票否决候选 |
| P4 | 沟通节奏差 | 回复频率、深度、主动性差异 | 体验预测 |
| P5 | 生活时间重合度 | 空闲时间与活动节奏 | 现实可执行性 |
| P6 | 情感需求匹配 | 需求与供给是否相互满足 | 关系满足度 |
| P7 | 双向投入平衡 | 发起、回复、追问、拒绝 | 关系是否能持续 |
| P8 | 冲突修复潜力 | 双方恢复沟通的能力 | 中期稳定性 |
| P9 | 特征置信度 | 证据覆盖、时效和质量 | 控制低质量匹配 |
| P10 | 安全风险 | 举报、骚扰、越界行为 | 安全硬约束 |
| P11 | 成长同向性 | 成长方向、速度、支持度和修正意愿的差异 | 长期可持续性 |
| P12 | 时间边界兼容度 | 回复预期、独处需求、守约和时间安排的差异 | 降低时间压迫 |
| P13 | 空间与自主尊重 | 社交、隐私、独处和关系节奏边界是否被尊重 | 降低控制和窒息风险 |

注意：相似不等于兼容。部分维度需要相似，例如核心价值观；部分维度可能需要互补，例如主动与回应。权重必须从真实结果中学习，不能长期依赖人工拍脑袋。

## 7. 匹配计算与用户界面表达

### 7.1 内部计算

硬约束不通过时，不产生推荐：

```text
P1 == false => recommendation = false
```

通过硬约束后，目标是估计：

```text
P(关系结果良好 | A、B、当前状态、互动过程、推荐策略)
```

内部可以维护以下字段：

```text
ranking_score
success_probability
confidence
explanation_factors
```

这些字段只用于内部排序、实验、校准和生成解释，不直接暴露给用户。内部排序可以存在，但它只表示当前策略下的展示顺序，不代表人的价值、关系命运或确定性结论。

### 7.2 用户界面表达规范

用户界面必须遵守以下规则：

1. 描述“目前看到的信号”，不描述“用户是什么样的人”。
2. 使用“可能”“更接近”“还需要确认”等暂定表达。
3. 同时给出正向线索、差异线索和未知信息。
4. 不使用固定人格标签、诊断性词汇或隐喻式定性。
5. 不展示匹配百分比、星级、等级、胜率或“灵魂伴侣概率”。
6. 不展示“最匹配”“命中注定”等暗示确定性的措辞。
7. 每个解释必须能追溯到用户选择、用户确认内容或产品内互动。
8. 用户可以对解释进行“更像”“不像”“不确定”的反馈和修正。

推荐卡片不应使用“匹配度 87%”或“人格标签：独立、慢热”，而应使用以下结构：

```text
目前看到的共同点
可能需要进一步确认的差异
现在仍然不知道的事情
你可以怎样继续了解
```

示例：

```text
你们在“保留独处时间”上的选择比较接近。
这可能意味着双方都需要一定空间，但还不足以判断相处感受。
可以继续留意：忙碌时如何保持联系感，以及规划变化时如何说明。
```

### 7.3 推荐排序原则

- 排序用于决定展示顺序，不用于给用户打分。
- 界面默认不解释排名语义，不显示“第 1 名”或“最匹配”。
- 推荐结果必须同时保留探索性位置，避免系统不断强化既有偏好。
- 排序发生变化时，用户看到的是新的关系线索，而不是一个上下浮动的分数。

## 8. 内部结果变量

以下“标签”仅指训练和评估模型使用的结果变量，不是展示给用户的人格标签，也不能直接出现在推荐卡片中。

| 时间尺度 | 结果变量 | 示例 |
|---|---|---|
| 即时 | `y_accept` | 双方是否愿意继续了解 |
| 短期 | `y_conversation_7d` | 7 天后是否持续交流 |
| 中期 | `y_satisfaction_14d` | 14 天后双方是否满意 |
| 中期 | `y_growth_alignment_30d` | 30 天后是否仍认可彼此的成长方向和节奏 |
| 中期 | `y_boundary_respect_30d` | 30 天后是否感到时间、空间和边界被尊重 |
| 长期 | `y_meetup` | 是否在双方同意下现实见面 |
| 长期 | `y_relationship` | 是否建立稳定关系 |
| 安全 | `y_safety_event` | 举报、拉黑、骚扰或越界 |

v0.1 主标签建议定义为：

```text
good_outcome_14d =
  y_satisfaction_14d == positive
  AND no confirmed safety event
  AND continued_contact
```

30 天扩展标签：

```text
good_outcome_30d =
  good_outcome_14d
  AND y_growth_alignment_30d == positive
  AND y_boundary_respect_30d == positive
```

阈值必须通过用户访谈和问卷校准，不能随意写死。

## 9. 指标体系

### 9.1 数据质量

- Claim 覆盖率
- 证据覆盖率
- 平均置信度
- 过期特征比例
- 用户纠正率
- 来源可追溯率
- 缺失率和重复率

### 9.2 模型质量

- PR-AUC：处理正负样本不均衡
- NDCG@K：衡量推荐顺序
- 校准误差：预测概率是否可信
- 双向匹配率
- 不同人群的错误率差异

### 9.3 界面表达质量

- 固定人格标签违例数，目标为 0
- 用户可见的匹配百分比或星级数量，目标为 0
- 解释中包含差异和未知信息的比例
- 解释可以追溯到证据的比例
- 用户使用“更像 / 不像 / 不确定”进行修正的比例
- 用户正确理解“推荐不是确定性结论”的比例

### 9.4 产品结果

- 双向有效匹配率
- 首轮回复率
- 7 天对话存活率
- 14 天双向满意度
- 30 天成长同向满意度
- 时间、空间和边界被尊重比例
- 现实见面率
- 退出率和撤回授权率

### 9.5 安全护栏

- 举报率
- 拉黑率
- 骚扰与越界事件率
- 过度曝光率
- 边界侵犯投诉率
- 删除请求处理时间
- 未授权数据使用事件数

## 10. 事件与数据契约

每次推荐至少记录：

```text
event_id
user_id
candidate_id
session_id
event_type
event_time
rank
position
model_version
policy_version
context
consent_scope
```

核心数据表：

```text
users
consents
raw_documents
evidence
claims
feature_snapshots
pair_features
impressions
actions
matches
conversations
outcomes
model_versions
policy_versions
```

`policy_version` 用于识别曝光策略造成的选择偏差。没有它，无法可靠进行反事实评估。

## 11. 冷启动实验

第一阶段只使用两类来源：

1. 用户主动填写的场景取舍题。
2. 产品内部的曝光和选择行为。

比较三个基线：

- 基础关系信号与硬规则。
- 文本表示相似度。
- Claim 关系信号加行为信号。

建议样本：

- 30–50 名首批用户。
- 每人 20–40 个高信息增益问题。
- 至少 50–200 次可控曝光。
- 收集 7 天和 14 天结果。

所有实验必须记录曝光策略，并保留一定比例的探索性推荐，否则模型只会学习已有策略产生的偏差。

## 12. 合规红线

- 敏感个人信息需要单独同意和明确目的。
- 第三方聊天中的其他参与者享有人格和隐私权益。
- 默认不存储完整第三方聊天原文。
- 原始数据必须加密，权限按最小必要原则控制。
- 用户必须可以撤回、删除和查看影响匹配的推断。
- 不应根据行为暗中推断性取向、健康、宗教、政治倾向等敏感属性。
- 数据保留期限、跨境传输和第三方处理方必须单独评审。
- 在中国场景下重点评估《个人信息保护法》及相关推荐算法、数据安全要求。

## 13. v0.1 验收标准

1. 每个关系信号都有数据来源、证据、置信度、时效性和修正方式。
2. 每个内部结果变量都有采集方式和时间窗口。
3. 没有未经授权的第三方原始聊天进入训练集。
4. 内部模型可以输出概率和置信度，但用户界面不得直接展示数字匹配度。
5. 推荐解释包含正向线索、差异线索和未知信息，不使用固定人格标签。
6. 推荐事件包含模型版本和策略版本。
7. 安全事件可以覆盖或否决普通匹配结果。
8. 成长同向性和时间/空间边界尊重均有关系信号、结果变量和验证方式。
9. 文档对应的数据契约测试全部通过。
